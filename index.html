A Megakernel per Model

Claude wrote a GPU inference engine for each of five open models. How much faster they are than vLLM and SGLang, how that was measured, and how the agents got there.

Nov 16, 2026 · interim results · figures and tables are generated from job logs · all measurements and every run

TL;DR

General inference engines such as vLLM and SGLang serve every model through one scheduler and one library of kernels. We asked what happens when the engine is instead written for a single checkpoint on a single card, as one GPU kernel that never hands control back to the host between tokens (a megakernel), and when a coding agent writes it. For five open models, from 8 B to 594 B parameters, an agent in an autoresearch loop wrote such an engine against an evaluator it could not change: 12 runs, 264 agent-hours, 412 evaluated submissions.

Steady decode. With the checkpoint's own number formats (track A), the engines are 1.08–1.43× as fast as the fastest general engine with one sequence on all five models, and at least 1.10× with both one and eight sequences on 3 of them (Qwen3-8B, flint and Inkling-2-Small). Serving a production trace on Inkling-2-Small and four B200 cards, at 1 to 4 requests per second, 100% of requests stay within the service levels against 83–85% for SGLang, and the longest stall is 0.08–0.09 s against 2.3–2.8 s.

When the agent may also choose how the model is stored, without changing what it computes (track B), the factor with one sequence reaches 1.68×. The engines are narrower than a general engine: the fastest ones hold 8 sequences and a 2,048-token context, and the ones built for serving decode more slowly. Both limits are measured below.

Results on steady decoding

The benchmark is the one inference engines are usually compared on: a 64-token prompt, 1,024 generated tokens, greedy decoding, with one sequence or with eight in a batch. Figure 1 gives the speed of our engines relative to the fastest general engine on the same card.

With one sequence, track A is 1.08 to 1.43 times as fast as the fastest general engine, on every model. With eight sequences the advantage is smaller, and on North Mini Code (1.02×) and Qwen3.8-27B (1.04×) it is below the 1.10× we had set as the target for both batch sizes. Track A reaches that target on Qwen3-8B, flint and Inkling-2-Small; track B reaches it on Qwen3-8B, North Mini Code, Qwen3.8-27B and Inkling-2-Small.

For North Mini Code the fastest general engine is not vLLM but the megakernel Cohere wrote by hand for this model. Against vLLM, track A is 1.99× and 1.37×.

The two tracks

An engine written for one model can be faster for two different reasons, and we report them separately.

Track A changes only how the computation is organised on the card. The weights are the checkpoint's, in the checkpoint's formats (BF16, or the 4-bit and 8-bit formats of a quantized checkpoint). Activations and the K/V cache use the formats the general engines use. Every operator runs for every token, and one token is produced per pass over the model. A track-A number answers the question: the same computation, how much faster?

Track B also lets the agent change how the model is stored and what is computed once at load time, provided the function stays the same in exact arithmetic. Quantizing, pruning or approximating weights or activations is not allowed. Track B passes the same accuracy tests as track A. Two of the five track-B engines give logits that are bit-identical to their track-A build. The other three keep some intermediate values in float32 where the standard implementation rounds to BF16, so they are at least as precise but differ in the last bits; Figure 1 draws them outlined, and Table 6 says what each one does.

How the comparison is made

Speed comparisons between inference engines are easy to get wrong. The procedure is the same for every system.

  • One card, one job. All systems of a comparison run in the same job on the same card (for Inkling-2-Small, the same four-card node), one after another. Each round starts every server afresh and begins with a different system. There are three rounds, each with one warm-up and three timed repeats.
  • One interface, one client. Every system is served through an OpenAI-compatible streaming HTTP endpoint and timed by the same client, which records the arrival of each token. Our engines sit behind a small front-end process that streams one chunk per token and detokenizes incrementally, so the cost of serving is included on both sides.
  • The same work. Prompts are sent as token ids, every request generates exactly 1,024 tokens (end-of-sequence is ignored), and the time per token is taken over the window in which all sequences are decoding.
  • Released baselines with their recommended settings. vLLM and SGLang are installed from their releases and run with the flags of their own recipes; where we found a faster setting we used it (Table 1). The reference in Figure 1 is whichever of them is fastest on that model.
  • Correct before timed. An engine gets a time only after its logits agree with a float64 implementation of the model, position by position, to within twice the error of the standard BF16 implementation, and its greedy tokens agree as well.

How the agents got there

Each engine comes from one or more autonomous runs. A run gives Claude (Opus 5.5 or Fable 5.2, in Claude Code) the checkpoint, a GPU pod with the card, and a budget of 3 to 40 agent-hours. The agent profiles and experiments on the card as it sees fit and submits source code whenever it wants a score. A submission is built and scored by an evaluator the agent cannot modify: first the correctness tests, then the timing. Every submission is recorded with the hypothesis the agent wrote for it and with its result. The prompt states the goal, the rules and the tools, and names no optimization technique.

The runs follow a similar course. The first engine that passes the tests is slower than the fastest general engine. The first large step is to put the whole decode step into a single kernel and to lay the weights out in the order the tensor cores consume them. Most of what follows is work on the memory system: which loads go through the L1 and L2 caches, what is prefetched during which phase, how many registers a thread holds, and what the idle thread blocks do while attention runs. The engine overtakes the general engines within about three hours on Qwen3-8B, North Mini Code and flint, after seven hours on Inkling-2-Small and after nineteen on Qwen3.8-27B.

On Inkling-2-Small the Fable 5.2 run for track A started from the Opus 5.5 run's engine at its 5.5-hour mark, with that run's records to read, and within four hours it had passed the point the Opus run reached in 24.

Decoding one sequence is limited by how fast the card can read the weights. On Qwen3-8B and an H100, reading the 15.1 GB of BF16 weights once takes 4.52 ms at the card's memory bandwidth. The track-A engine of that run ended at 5.23 ms, 86% of that limit.

What a single checkpoint allows

Track B is where an engine for one checkpoint uses facts that a general engine cannot assume (Table 6). The clearest case is the weight format. BF16 has eight exponent bits, but the weights in one row of a trained matrix span only a few powers of two. The agent working on Qwen3-8B measured this, stored each weight in 12 bits, and had the kernel decode them in registers on the way to the tensor cores. The engine then reads a quarter fewer bytes per token, and its time fell below the limit quoted above for 16-bit weights. Later runs could read the records of earlier ones, and the agents on North Mini Code and Qwen3.8-27B adapted the code to their models; the version on Qwen3.8-27B is arranged so that every result is bit-identical to BF16 arithmetic.

The same search finds little where the checkpoint has already been compressed: Inkling-2-Small stores its experts in 4 bits, and track B gained 0.6% there. On Qwen3.8-27B one run also used the checkpoint's own draft head to produce several tokens per pass and verify them exactly; on natural text that engine decodes at 3.71 ms per token, 2.4 times as fast as its track A.

Serving live traffic

The engines above decode a batch that starts together. A server has to accept requests while others are running. For Qwen3-8B and Inkling-2-Small a second run extended the engine: requests are admitted as they arrive, prompts are processed in chunks inside the kernel, K/V memory is paged, and prompt prefixes shared between requests are reused. The test is a replay of the Mooncake trace of tool-and-agent traffic, whose prompts average about 9,000 tokens, with both systems behind HTTP on the same node.

At 1, 2 and 4 requests per second the megakernel keeps 99.9 to 100.0% of requests within the service levels and SGLang 82.7 to 85.4%. The difference comes from stalls. When a long prompt arrives, SGLang's decoding requests wait for it: its longest stall is 2.3 to 2.8 s and the 99th percentile of the time between tokens is 697 to 796 ms. For the megakernel these are 0.08 to 0.09 s and 68 to 72 ms.

On the other measures the megakernel is slower. Its median time between tokens is 28 to 44 ms against 9 to 10 ms, and its 99th-percentile time to the first token is 3.4 to 3.9 s against 2.2 s. At 8 requests per second it no longer keeps up: 34% of requests are within the service levels, where SGLang still has 82%. The audit of the engine traces both sides to one mechanism. Each pass over the model carries decoding rows and prompt positions together, and its size is limited by how long the decoding requests can wait. This bounds the stalls, and it also limits how fast prompts are processed. Plain steady decoding with this engine takes 11.4 ms per token, against 4.7 ms for SGLang and 3.3 ms for the steady-decode engine it was built from.

On Qwen3-8B and one H100 the result has the same shape, and here the serving engine is not slower at plain decoding either. At 1 and 2 requests per second it keeps 95 to 97% of requests within the service levels, against 68 to 75% for SGLang and vLLM; at 3 it keeps 90 to 93% against 59 to 68%, and at 4, where no system keeps up, 64 to 68% against 13 to 17%. Its longest stall is 0.09 to 0.13 s, where vLLM's is 0.5 to 1.2 s and SGLang's 6.2 to 9.2 s. The price is again the slowest first tokens: at 1 and 2 requests per second the 99th percentile is 7.2 to 8.0 s against 5.5 to 6.0 s.

Limits, and what the audits changed

The steady-decode engines were built for the benchmark of Figure 1 and are narrow outside it. They hold at most 8 sequences and a context of 2,048 tokens, feed the prompt one token per pass, and decode greedily inside the kernel (sampling is done outside it and costs 1 to 11%). Figure 6 shows Inkling-2-Small when one setting at a time moves away from the benchmark.

Every final engine was read by an independent agent that looked for rule violations and ran its own verification jobs. No engine calls another engine, caches outputs, recognises the evaluator's inputs or skips part of the model. The audits did change what we report, and three runs were extended or repeated because of them.

  • Multi-token decoding. The evaluator reported 0.415 ms per token on Qwen3.8-27B. Two of its three timed prompts lead the model into a two-token loop, which the drafts predict almost perfectly. On natural text the figure is 3.71 ms, and that is the one we report.
  • Track B on three models. The track-B engines of Qwen3-8B, North Mini Code and flint do not give the logits of track A: flint's differs at every one of 14,336 positions checked and picks a different top token at 10.8% of them. They are more precise than the BF16 path and pass the accuracy tests, but the evaluator took the label on trust. We now mark them separately.
  • Behaviour past the context limit. Beyond about 2,000 positions the steady-decode engine for Inkling-2-Small overwrote other sequences' K/V memory, and flint's returned no tokens, in both cases without reporting an error. Both runs were extended. The final engines refuse such requests, and follow-up audits found their logits bit-identical to those of the engines audited first.
  • A test added after a run. The first run, on Qwen3-8B, ended before the evaluator checked positions beyond 128. Under the final evaluator its track-A engine failed at one of 1,024 later positions (an error of 1.18 against a limit of 1.07). A three-hour run found the cause: the engine rounded every attention score to BF16 twice, as the Hugging Face "eager" attention does, where the default attention path keeps scores in float32. With float32 scores the median error at those positions is 0.016, equal to that of the BF16 implementation, and the speed is unchanged. Figure 1 shows the corrected engine. The audit of the correction adds a caution about the test itself: the largest error over a thousand positions comes from a heavy tail, and on three other sets of sequences the corrected engine exceeded twice the BF16 implementation's largest error on one set and the old engine on another. The median is the comparison that holds; a limit on the largest error decides little.
  • Serving engines that trust their caller. The first serving engine for Inkling-2-Small wrote out of bounds when built for fewer than 64 sequences and matched shared prompt prefixes by a 64-bit hash without comparing the tokens. Its run was extended; the final engine compares prefixes token by token and refuses requests beyond its limits, and the follow-up audit confirmed both, with 130 concurrent requests giving the tokens of each request alone. The serving engines for Qwen3-8B still have these defects: a token id outside the vocabulary crashes the engine, a request longer than the context writes into another request's page table, and for the prefix hash the auditor constructed two prompts with the same value, the second of which received the first one's answer. The steady-decode engine for Qwen3.8-27B likewise crashes on an invalid token id or on a batch of nine. mkserve validates every request before an engine sees it. The prefix hash on Qwen3-8B is not fixed.
  • Tokens under load. With the track-A serving engine for Qwen3-8B, a request's tokens under heavy concurrent load differed from the same request alone in 12 of 17 trials, from a near-tie between two tokens onwards. The cause was not found. With track B they were identical in 24 of 24.
  • flint's own request path. A single request with a prompt of 800 tokens or more fails with an error in the engine's request path. mkserve steps the engine instead and serves such prompts.

All of these passed the evaluator of their run, whose test prompts were synthetic, whose check of served tokens was loose, and which never sent a request at or beyond an engine's limits.

Next

The evaluation is being extended with natural-text prompts, an exact comparison of the tokens that are served, a bit-for-bit test for track B, and a float64 reference out to 32,000 positions. On the engineering side the open problem is a serving engine whose small passes are as fast as the steady-decode kernel. The run on flint has been extended to work on batches of eight.
